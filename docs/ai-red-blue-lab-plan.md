# AI Red vs Blue Security Lab — 개발 계획

## 1. 프로젝트 목표

격리된 실험 환경에서 정적 분석, 탐지 규칙 생성, 공격 기법 모의실행, 방어 규칙 개선을 자동화하는 개인용 보안 연구 프레임워크를 만든다.

핵심 목표는 단순한 "AI가 보안 코드를 작성한다"가 아니라 다음 흐름을 하나의 반복 가능한 실험 체계로 구현하는 것이다.

1. 파일과 로그에서 특징 추출
2. 정적 분석 및 위험도 평가
3. 방어 AI가 탐지 규칙 제안
4. 격리된 샌드박스에서 사전 정의된 공격 시나리오 실행
5. 블루팀이 탐지 및 대응
6. 심판 모듈이 탐지율·오탐률·탐지시간 평가
7. 결과를 바탕으로 탐지 규칙 개선
8. 같은 시험을 반복해 개선 폭 측정

이 프로젝트는 교육·방어 연구 및 포트폴리오 목적이며, 실제 외부 시스템 공격이나 인터넷상 공격 자동화를 목표로 하지 않는다.

## 3. 주요 구성요소

### 3.1 정적 분석 엔진

초기 MVP의 핵심 기능.

분석 항목 예시:

- SHA-256 해시
- 파일 크기 및 형식
- PE 헤더 및 섹션 정보
- 가져오기/내보내기 함수
- 문자열 추출
- 섹션별 엔트로피
- 디지털 서명 여부
- 비정상 섹션명 및 권한
- 난독화 또는 패킹 의심 특징
- YARA/YARA-X 규칙 결과

출력은 JSON으로 통일해 이후 AI가 안정적으로 읽을 수 있게 한다.

예시:

```json
{
  "file": "sample.exe",
  "sha256": "...",
  "entropy": 7.4,
  "imports": ["CreateProcessW", "VirtualAlloc"],
  "signed": false,
  "yara_matches": [],
  "risk_features": []
}
```

### 3.2 블루팀 AI

역할:

- 정적 분석 결과 요약
- 의심 특징 설명
- YARA/YARA-X 탐지 규칙 제안
- Sigma 로그 탐지 규칙 제안
- 기존 규칙의 오탐 원인 분석
- 이전 라운드에서 놓친 패턴 분석
- 새 규칙 적용 전/후 성능 비교

중요 원칙:

- AI의 규칙은 즉시 신뢰하지 않고 자동 시험을 거친다.
- 탐지율뿐 아니라 오탐률도 같이 평가한다.
- 규칙 변경 이력을 모두 남긴다.

### 3.3 레드팀 AI

초기에는 실제 악성코드 생성이 아니라 **사전 정의된 안전한 공격 시뮬레이션을 선택·조합하는 역할**만 담당한다.

예시 범위:

- 파일 생성/변경
- 의심스러운 프로세스 실행 모의
- 스크립트 실행 이벤트 생성
- 특정 경로 접근
- 테스트용 레지스트리 변경
- 테스트용 네트워크 요청
- 로그 흔적 변형

레드팀의 목표는 "피해를 주는 코드"가 아니라 "블루팀 탐지 규칙의 빈틈을 찾는 시험 입력"을 만드는 것이다.

### 3.4 샌드박스

필수 안전장치.

초기 환경 후보:

- Windows Sandbox
- Hyper-V VM
- 별도 Windows 가상머신
- WSL2는 분석 도구 실행용으로 사용하되 위험 샘플 실행은 별도 VM 사용

필수 정책:

- 외부 인터넷 차단 또는 제한
- 호스트 공유폴더 금지
- 클립보드 공유 최소화
- 호스트 자격증명 전달 금지
- 시험마다 스냅샷 복원
- 실험 데이터와 개인 파일 완전 분리
- 실험용 가상 네트워크 사용

### 3.5 심판 / 평가 모듈

모든 라운드의 성능을 수치화한다.

주요 지표:

- 탐지율
- 미탐률
- 오탐률
- 평균 탐지시간
- 규칙 수
- 규칙 복잡도
- 라운드별 개선 폭

예시:

```text
Round 1
Detection Rate : 61%
False Positive : 14%
Mean Detect Time: 3.2s

Round 20
Detection Rate : 89%
False Positive : 4%
Mean Detect Time: 1.1s
```

이 지표는 포트폴리오에서 프로젝트 가치를 보여주는 핵심 자료로 사용한다.

## 4. 참고할 공개 기술

직접 상용 백신을 복제하지 않고 공개 생태계를 조합한다.

- YARA / YARA-X: 파일 패턴 탐지
- Sigma: 로그 기반 탐지 규칙
- Ghidra: 바이너리 분석 및 역공학
- pefile / LIEF: PE 구조 분석
- capa: 실행파일 기능 특징 분석
- Suricata: 네트워크 탐지
- Zeek: 네트워크 행위 분석
- MITRE ATT&CK: 공격 기법 분류 및 안전한 시나리오 설계 참고
- Kaspersky KLara: 대량 YARA 검사 구조 참고

카스퍼스키의 상용 백신 소스 전체가 오픈소스인 것은 아니므로, 공개된 KLara 등의 구조와 아이디어만 참고한다.

## 7. 포트폴리오에서 보여줄 것

단순히 코드 양을 늘리는 것이 아니라 다음 결과를 증명하는 것을 목표로 한다.

### 기술적으로 보여줄 수 있는 능력

- Python 개발
- Windows / WSL2 환경 구성
- 실행파일 구조 분석
- 탐지 규칙 작성
- 로그 분석
- 가상화 및 샌드박스 설계
- AI API 또는 로컬 LLM 연동
- 에이전트 간 역할 분리
- 자동 평가 파이프라인
- 보안 실험 설계
- 데이터 시각화

### 최종 README에 들어갈 핵심 결과

```text
Test Samples       : 1,000
Initial Detection  : 61%
Final Detection    : 89%
Initial FP Rate    : 14%
Final FP Rate      : 4%
Rounds             : 20
```

실제 측정값이 생기기 전에는 임의의 수치를 결과처럼 게시하지 않는다.

## 8. 안전 원칙

1. 외부 시스템을 대상으로 자동 공격하지 않는다.
2. 공격 시뮬레이션은 소유한 격리 환경에서만 실행한다.
3. 실제 사용자 자격증명이나 개인정보를 테스트 데이터로 사용하지 않는다.
4. 실제 악성코드를 GitHub 저장소에 업로드하지 않는다.
5. 위험 샘플을 다루게 될 경우 저장소에는 해시와 분석 결과만 기록한다.
6. 테스트 VM과 개인용 Windows 환경을 분리한다.
7. AI가 생성한 코드는 실행 전 정책 검사를 거친다.
8. 레드팀 에이전트에는 인터넷 대상 탐색·전파 기능을 부여하지 않는다.

## 9. 첫 번째 구현 목표

가장 먼저 만들 것은 **AI가 아니라 정적 분석기**다.

첫 번째 버전의 성공 기준:

```text
입력: Windows PE 파일
  ↓
파일 특징 자동 추출
  ↓
YARA 검사
  ↓
JSON 보고서 생성
  ↓
AI가 보고서 요약 및 의심 지점 설명
```

여기까지 완성하면 이미 독립적으로 보여줄 수 있는 포트폴리오 결과물이 된다.

그 다음 단계부터 블루팀 자동화 → 안전한 레드팀 시뮬레이터 → 자동대전 순서로 확장한다.

## 10. 프로젝트의 최종 방향

최종 목표는 다음 질문에 실제 실험 결과로 답할 수 있는 시스템을 만드는 것이다.

> "격리된 환경에서 AI 공격 시뮬레이터와 AI 방어 에이전트를 반복 경쟁시키면 탐지 규칙이 실제로 개선되는가?"

코드를 만드는 것 자체보다 **가설 → 실험 → 측정 → 개선**의 과정을 GitHub에 남기는 것을 최우선으로 한다.
